# ADR-0008 — Machine identity is stable, opaque and independent from mutable host metadata

**Status:** Accepted  
**Date:** 27 September 2026

## Context

GameSaveSync must distinguish machines reliably across:

- hostname changes;
- Windows user changes;
- workgroup/domain changes;
- path changes;
- operating-system reinstalls;
- replacement/retirement of machines;
- addition of new machines to an existing game profile.

A machine name or username cannot be the identity.

Example:

- `Wall-E` may be reformatted and renamed `TERMINATOR`;
- it may still represent the same logical GameSaveSync machine and should retain the same machine identity;
- a new PC such as `Eve` must receive a distinct identity and must never implicitly replace `Wall-E`.

Per-machine path overrides also require a stable key even when usernames or local paths change.

## Decision

Introduce `MachineId` as the stable logical identity of a GameSaveSync machine.

`MachineId` is:

- opaque;
- immutable;
- globally unique within the GameSaveSync server authority;
- independent from hostname, username, workgroup, IP address, hardware details and filesystem paths;
- suitable as the durable key used by per-machine configuration and future registrations.

H2 introduces the value object and uses it where a machine identity is already required, especially per-machine path overrides.

### Representation and generation authority

`MachineId` stores a non-empty .NET `Guid`.

A new logical machine identity is generated by the authoritative Application/Server enrollment workflow, with UUID v7 (`Guid.CreateVersion7()`) as the accepted generation strategy.

Responsibility is deliberately split:

- Core validates/transports an existing non-empty GUID;
- Application/Server decides when a new logical identity must be created and generates it;
- Persistence stores the identity it is given;
- SQLite does not create an autoincrement/IDENTITY substitute for MachineId;
- the Agent does not self-assign a new authoritative MachineId.

An authorized rebind after reinstall reuses the existing GUID rather than creating a replacement identity.

## Logical machine vs installation

A MachineId identifies the logical machine record, not a particular Agent installation.

Reinstalling Windows or reinstalling the Agent does not inherently require a new MachineId.

However, a fresh installation must not automatically claim an existing MachineId based on hostname, username or hardware heuristics.

Future Agent/Admin work must provide an explicit, authorized re-enrollment/rebinding flow when a reinstalled machine should continue using an existing MachineId.

Conceptually:

```text
Wall-E
MachineId = M1
hostname = WALL-E

reformat / reinstall / rename

TERMINATOR
MachineId = M1   <- explicit rebind to the existing logical machine
hostname = TERMINATOR
```

By contrast:

```text
Eve joins later
MachineId = M2   <- always a distinct logical machine
```

## Mutable metadata

Future machine metadata may include values such as:

- hostname/display name;
- Windows username;
- workgroup/domain;
- Agent version;
- last-seen timestamp;
- capabilities.

Those values are descriptive and mutable.

They are never identity.

Username is specifically expected to matter for resolving per-machine paths, but changing the username/path must not change MachineId.

## H2 scope

H2 does not introduce a full machine registry.

H2 scope is:

- add the `MachineId` value object;
- replace raw machine-id strings where the existing domain already requires identity;
- persist/use MachineId GUID values in profile path overrides when profile persistence is implemented.

H2 does not yet define:

- machine registration protocol;
- machine credentials;
- re-enrollment/rebinding transport;
- retirement/deletion workflow;
- hostname/username metadata schema;
- Agent trust/authentication.

Those belong to later Agent/Admin work where the real consumer exists.

## Persistence direction

Until the machine registry exists, a path override may persist MachineId as an opaque value without a foreign key to a `machines` table.

When H3 introduces the registry, the database may add a machine table and relationships via an explicit migration.

The migration must preserve all existing MachineId values.

## Security implication

A reinstalled Agent claiming an existing MachineId is security-sensitive.

The future flow must require explicit server/admin authorization or possession of a trusted recovery/enrollment mechanism.

Matching mutable metadata or hardware fingerprints is not sufficient proof of identity.

## Consequences

Benefits:

- path overrides remain stable across renames/reinstalls;
- adding a new machine cannot accidentally replace an existing one;
- identity survives mutable host metadata;
- future machine registry can grow without changing identity semantics.

Costs:

- reinstall/re-enrollment needs an explicit recovery flow;
- machine identity must be persisted safely by the Agent/server;
- user-facing names and MachineId become separate concepts that UI must present clearly.
